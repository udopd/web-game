# 2. Главные правила реализации

## 2.1. Не создавать MVP

Не предлагай MVP.

Не ограничивайся минимальным вертикальным срезом.

Не останавливайся после реализации базового перемещения персонажа, одного оружия или демонстрационного редактора.

Проект должен содержать всю функциональность, предусмотренную спецификацией.

Разрешается реализовывать проект последовательно, но каждый этап является частью единого плана разработки полного продукта, а не самостоятельным урезанным результатом.

Завершение этапа не означает завершения проекта.

## 2.2. Запрет на фиктивную функциональность

Недопустимы:

- декоративные кнопки без обработчиков;
- страницы без реальных функций;
- фальшивые API;
- статические данные вместо серверных;
- поддельные игровые комнаты;
- симуляция мультиплеера исключительно в браузере;
- статистика, вычисляемая только клиентом;
- фиктивные прогресс-бары;
- неподключенные редакторы;
- JSON, которые не используются игрой;
- настройки, не влияющие на поведение системы;
- заглушки `TODO` вместо обязательной реализации;
- пустые функции;
- обработчики, возвращающие заранее подготовленный успешный результат;
- временные хардкодные массивы вместо реестров данных;
- UI, который выглядит работающим, но не сохраняет изменения.

Каждая кнопка, вкладка, настройка и операция должны иметь реальное назначение.

Каждое редактирование игрового контента должно доходить до соответствующего JSON и после публикации влиять на игровой процесс.

Если обязательная функция не реализована или не протестирована, нельзя обозначать ее как готовую.

## 2.3. Честная отчетность

Не объявляй проект завершенным без проверки.

Не утверждай, что тесты пройдены, если они не запускались.

Не утверждай, что мультиплеер работает, если не проверено реальное взаимодействие нескольких клиентов.

Не маскируй ошибки временными данными.

Если отсутствует внешняя зависимость, доступ к сервису, секрет, графический ресурс или системная возможность, зафиксируй конкретную проблему и реализуй все части, которые объективно можно завершить.

Не заменяй неработающую функцию декоративным аналогом.

Постоянно работающий сервер.

# 4. Data-Driven Architecture

**Весь игровой контент должен управляться данными.**

Персонажи, оружие, враги, боссы, сундуки, мутации, эффекты, анимации, частицы, декорации, карты и последовательности уровней не должны быть жестко зашиты в код.

Каждая предметная область имеет отдельный JSON-файл.

Все JSON должны иметь:

- schemaVersion;
- типизированную структуру;
- уникальные ID;
- проверяемые ссылки;
- ограничения характеристик;
- валидаторы;
- документированные правила совместимости.

Создай универсальный `ContentRegistry`.

Реализуй полный цикл:

1. Создание объекта в редакторе.
2. Настройка параметров.
3. Привязка ресурсов.
4. Предпросмотр.
5. Валидация.
6. Сохранение черновика.
7. Экспорт JSON.
8. Формирование ZIP.
9. Публикация версии.
10. Автоматическая загрузка в игру.
11. Использование данных игровой симуляцией.

Создай систему immutable content packs.

Активный забег должен использовать зафиксированную версию контента.

При загрузке игры автоматически проверять manifest, целостность файлов и совместимость схем.

Поддерживать импорт ранее экспортированного архива без потери данных.

# 7. Custom Mutation SDK

Особое внимание удели:

`CUSTOM_MUTATION_PIPELINE.md`

Реализуй три режима создания мутаций:

1. JSON Configuration.
2. Visual Logic Graph.
3. Custom TypeScript Handler.

Новые мутации должны создаваться с минимальным количеством изменений исходного кода.

Для стандартных эффектов изменение кода не требуется.

Для новых уникальных механик использовать расширяемый SDK.

Создай автоматическую регистрацию обработчиков, схем параметров и редакторских инспекторов.

Сделай универсальный шаблон создания кастомной мутации с помощью ИИ.

Обязательны:

- типизированный MutationContext;
- жизненный цикл обработчика;
- события;
- детерминированные вычисления;
- контролируемая работа с игровыми сущностями;
- сериализация необходимого состояния;
- поддержка мультиплеера;
- очистка подписок;
- тестирование;
- версионирование;
- валидация конфигурации.

Не разрешай исполнять произвольный JavaScript из импортированного JSON или ZIP.

Custom TypeScript handlers должны собираться и публиковаться через доверенный процесс разработки.

# 8. Игровой процесс

Реализуй полноценную top-down roguelike-игру.

Основные системы:

- движение;
- прицеливание;
- стрельба;
- переключение оружия;
- подбор предметов;
- столкновения;
- физика снарядов;
- повреждения;
- статусы;
- мутации;
- опыт;
- прогрессия;
- процедурные уровни;
- боссы;
- переходы между биомами;
- смерть;
- победа;
- повторное прохождение.

Оружие должно различаться не только характеристиками, но и поведением.

Обычное пулевое оружие, дробовики и болтовое оружие создают снаряды.

Лазерное оружие использует систему лучей.

Ближний бой использует отдельную систему hitbox.

Реализуй систему противников с управляемым поведением, поиском цели, навигацией и атакой.

Враги и боссы могут иметь разные размеры и анимации подготовки атаки.

Процедурная генерация должна учитывать:

- seed;
- биом;
- сложность;
- правила размещения;
- доступность проходов;
- препятствия;
- декорации;
- сундуки;
- врагов;
- боссов;
- точки появления игроков.

Должны поддерживаться handcrafted, procedural и hybrid уровни.

### Игровой контент

Создай оригинальный стартовый набор контента, достаточный для полноценного прохождения и проверки всех систем.

Он должен демонстрировать все пять типов оружия, разные классы противников, боссов, мутации, биомы, сундуки, декорации, анимации, эффекты и прогрессию.

Не ограничивай игру одним тестовым помещением.

Не используй ресурсы Nuclear Throne или других игр без соответствующих прав.

Руководствуйся `AI_PIXEL_ART_GENERATION_GUIDE.md`.

При наличии инструментов генерации изображений используй их для создания оригинальных ресурсов. После создания проверяй соответствие размеров, прозрачности, кадров и технических требований.

# 9. Мультиплеер

Реализуй полноценный server-authoritative multiplayer.

Игра должна поддерживать кооператив на 2–4 игроков.

Обязательны:

- WebSocket;
- серверная игровая симуляция;
- синхронизация игроков;
- синхронизация врагов;
- синхронизация урона;
- синхронизация снарядов;
- генерация одного мира для всех участников;
- подключение по ссылке;
- создание лобби;
- владелец комнаты;
- готовность игроков;
- запуск владельцем;
- исключение участников;
- передача владельца;
- переподключение;
- завершение комнаты;
- восстановление активной сессии.

Клиент не может самостоятельно назначать нанесенный урон, убийства, выпавшие предметы или достигнутые уровни.

Сервер является источником истины.

Проверяй обработку задержек, потерь связи, повторных сообщений и несогласованных состояний.

# 10. Регистрация, сохранения и рейтинги

Реализуй минимальную регистрацию по имени.

Сервер должен создавать уникальный UID и защищенную пользовательскую сессию.

Имя игрока не должно выступать секретом аутентификации.

Все постоянные данные хранятся на сервере.

Обязательные данные:

- UID;
- имя;
- статистика;
- максимальный достигнутый уровень;
- общее количество убийств;
- количество смертей;
- игровые сохранения;
- открытые персонажи;
- настройки;
- история забегов.

Реализуй отдельные рейтинги по максимальному уровню и количеству убийств.

Обновление статистики выполняется только сервером.

Реализуй атомарное сохранение, контроль версий, восстановление активного забега и защиту от повторного учета событий.

### Настройки игры

Меню Settings должно включать:

- отдельную громкость музыки;
- отдельную громкость звуков;
- силу тряски камеры;
- управление;
- графические настройки;
- сброс сохранений.

Сброс сохранений должен требовать подтверждения.

Сброс прогресса не должен автоматически уничтожать UID или историческую статистику, если для этого не предусмотрена отдельная подтверждаемая операция.

# 12. Полная интеграция систем

Все основные игровые подсистемы должны быть связаны.

Примеры обязательных сценариев:

**Сценарий A — Оружие**

Администратор загружает спрайт → создает оружие → выбирает тип → настраивает снаряд → назначает звук → назначает частицы → тестирует стрельбу → публикует контент → новое оружие появляется в игре.

**Сценарий B — Мутация**

Администратор создает мутацию → выбирает триггер → настраивает эффект → тестирует его → экспортирует данные → публикует → мутация появляется в системе выбора улучшений.

**Сценарий C — Враг**

Администратор загружает спрайты → создает анимации → задает характеристики → назначает AI → настраивает атаку → задает награды → размещает врага в таблице генерации → публикует → враг появляется на уровнях.

**Сценарий D — Босс**

Администратор задает размер → анимации → фазы → паттерны → звуки → частицы → тряску камеры → награды → привязывает босса к кампании → тестирует → публикует.

**Сценарий E — Кампания**

Администратор создает биом → рисует карту → размещает декорации и сундуки → настраивает генерацию → создает цепочку уровней → добавляет босса → устанавливает условие разблокировки персонажа → публикует → игрок проходит кампанию и получает персонажа.

**Сценарий F — Мультиплеер**

Игрок регистрируется → создает комнату → отправляет ссылку → второй игрок входит → оба выбирают персонажей → владелец запускает забег → игроки совместно проходят уровни → результаты сохраняются сервером.

**Каждый сценарий должен быть подтвержден интеграционным или E2E-тестом.**

# 21. Главное архитектурное правило

**Игра, редактор и сервер должны образовывать единую согласованную систему.**

Редактор — инструмент создания игрового контента.

JSON — конфигурационный источник истины.

Общая симуляция — источник игровых правил.

Сервер — источник достоверного состояния забегов, прогресса и результатов.

Игровой клиент — средство взаимодействия и визуализации.

Необходимо добиться следующего результата:

Администратор заходит в редактор, создает нового персонажа, загружает и анимирует его спрайты, создает оружие, настраивает снаряды, добавляет врагов, настраивает босса, рисует уровни, задает последовательность прохождения, добавляет мутации, звуки и частицы, проверяет работу всего контента, экспортирует JSON-архив и публикует его.

Игрок открывает игру, регистрируется, выбирает доступного персонажа, создает лобби, приглашает друга и проходит созданную кампанию.

Все игровые события синхронизируются сервером, а достижения и статистика сохраняются в базе данных.

**Это конечная цель разработки.**
