# AI_PIXEL_ART_GENERATION_GUIDE.md

> **САМОСТОЯТЕЛЬНОЕ ТЗ И ПРОМПТ ДЛЯ ИИ-ГЕНЕРАЦИИ ГРАФИКИ.** Используется независимо от других документов и репозитория. Цель — производить согласованные, технически пригодные графические ресурсы для оригинального браузерного 2D pixel-art top-down roguelike shooter: игроки, враги, боссы, оружие, снаряды, лазеры, эффекты, частицы, декорации, разрушаемые объекты, сундуки, тайлы пола и стен, элементы интерфейса, и последовательности анимационных кадров.

**Не требуется** воспроизводить визуальный стиль, персонажей, оружие, логотипы, локации и спрайты Nuclear Throne. Это самостоятельный проект. Нельзя использовать охраняемые узнаваемые образы/логотипы/чужие наборы спрайтов без прав.

---

## 1. Роль генеративной модели / художника

Ты — lead pixel artist, technical artist и специалист по подготовке ассетов для 2D top-down видеоигр. Создавай **игровые ресурсы**, а не концепт-арт, скриншоты, иллюстрации или UI-макеты.

Каждый результат должен иметь:

- однозначную функцию в игре;
- заданные размеры canvas в пикселях;
- вид сверху или согласованный top-down/three-quarter-top ракурс;
- фиксированную пиксельную сетку и читабельный силуэт;
- цельный стиль и ограниченную палитру;
- прозрачность вне спрайта там, где она требуется;
- стабильные габариты, pivot и ориентацию для анимации;
- пригодность к импорту в покадровый редактор и JSON-манифест.

**Важное ограничение:** генеративная модель может создать изображение с ошибками пиксельной сетки, фоном вместо alpha, разными пропорциями между кадрами или несовпадением персонажа в анимации. Поэтому каждая генерация проходит техническую проверку и при необходимости ручную правку в пиксельном редакторе. Текстовый запрос сам по себе не гарантирует точный spritesheet.

## 2. Art direction — визуальный стандарт

### 2.1. Базовый стиль

- Жанр: яркий по геймплейной читаемости, но слегка мрачный и уютно-фантастический action roguelike.
- Камера: **top-down с небольшим видимым передним торцом** персонажей/объектов при необходимости; использовать одинаковый ракурс во всех наборах.
- Силуэты: ясно различимые на расстоянии, для каждого врага и героя — узнаваемый силуэт.
- Пиксельная сетка: каждый пиксель исходника воспринимается как отдельная ячейка; никаких размытых, дробных или акварельных линий.
- Освещение спрайтов: один условный свет сверху-слева; не рисовать сложные объемные тени, противоречащие игровой камере.
- Контур: 1 px либо локальный темный цвет, без толстых случайных обводок.
- Цвета: ограниченная палитра, 3–5 основных оттенков на материал; насыщенные акценты только для интерактивных/опасных деталей.
- Материалы: различимые — металл, ткань, камень, дерево, органика, кристалл — через пиксельные блоки и один-два читаемых блика.
- Без текста внутри игровых спрайтов, без псевдо-3D рендера, без 3D изометрии, без motion blur.

### 2.2. Рекомендуемая палитра для прототипа

| Назначение | Цвет |
|---|---|
| Очень темный контур | `#182330` |
| Тень/фон | `#29394A` |
| Нейтральный средний | `#536779` |
| Светлый блик | `#C6D1C8` |
| Растительность | `#5C8D69` |
| Светлая трава | `#96BF7A` |
| Металл/холодный | `#73ACB4` |
| Опасность/снаряды | `#EEB75A` |
| Урон/опасность | `#D87676` |
| Магия/энергия | `#A581D2` |

Это **рекомендации**, не обязательное жесткое ограничение: при создании биома можно сменить локальную палитру, сохраняя контраст между фоном, опасностью и объектами. Все ассеты одной серии используют один справочник цветов.

### 2.3. Правила читаемости

- Персонажи и враги должны иметь контур/контраст относительно плитки пола.
- Опасные снаряды врагов должны легко отличаться от союзных.
- Декорация не должна маскироваться под предмет для подбора.
- Сундук должен считываться как интерактивный объект, включая его закрытую и открытую форму.
- Снаряды в размере 4–12 px должны иметь простой силуэт без мелких деталей.
- Важные действия (`windup`, атака, урон, смерть) должны читаться при скорости игры, а не только на увеличенной картинке.
- Большой босс не должен закрывать телеграф атаки. Опасная область на полу должна иметь собственный читаемый предупреждающий цвет/паттерн.

## 3. Технические размеры и исходные файлы

### 3.1. Базовые рекомендации (можно изменить централизованно)

| Вид ассета | Логический размер | Формат |
|---|---:|---|
| Тайлы пола/стен | 16×16 px, опционально 32×32 | PNG с правильными краями |
| Маленький герой | 32×32 px canvas/кадр | PNG с alpha |
| Средний враг | 32×32 или 48×48 px/кадр | PNG с alpha |
| Крупный враг | 64×64 px/кадр | PNG с alpha |
| Босс | 96×96 или 128×128 px/кадр | PNG с alpha |
| Оружие | 16×16, 32×16 или 32×32 px | PNG с alpha |
| Снаряд | 8×8 или 16×16 px | PNG с alpha |
| Сундук | 32×32 или 48×48 px | PNG с alpha |
| Декорация | 16×16, 32×32 или 64×64 px | PNG с alpha |
| Частица | 4×4, 8×8 или 16×16 px | PNG с alpha |
| UI icon | 16×16 или 32×32 px | PNG с alpha |

**Canvas ≠ hitbox ≠ visible bounds:** персонаж может занимать только 22×26 px внутри canvas 32×32; hitbox задается в редакторе отдельно. Размер кадра всех анимаций одного объекта обязан быть одинаковым.

### 3.2. Правила экспорта

1. Итоговые PNG — без масштабирования с билинейной интерполяцией. При необходимости использовать nearest-neighbor.
2. Визуальные объекты — с реальным прозрачным фоном (alpha=0), **не** с шахматной подложкой, не с белым/черным цветным фоном.
3. Фоны и тайлы — **не обязаны** быть прозрачными: floor tile обычно непрозрачен, decals/overlays — прозрачны.
4. Использовать RGB/RGBA, сохранять неизменные пиксельные границы.
5. Если генератор выдает изображение крупнее, сначала привести пиксели к строгой сетке и проверить каждую анимацию. Одного `nearest neighbor` после произвольного AI-рендера недостаточно для чистого пиксель-арта.
6. Не менять canvas, pivot, ракурс, костюм, пропорции, цвет и расположение ног между кадрами.
7. Исключить лишние тени за пределами спрайта, если динамическая тень создается в игре отдельно.
8. Нельзя хранить несколько анимаций внутри файла без известной раскладки кадров/metadata.
9. Для отдельных кадров применить единую схему именования: `{entity}_{direction}_{animation}_{frameIndex:03d}.png`.
10. Сопровождать ассеты metadata: назначение, canvas, pivot, FPS/длительности кадров, направления, число кадров, лупинг, license/provenance.

## 4. Пайплайн генерации ассета

### Шаг 1 — заполнить Asset Brief

```yaml
asset_id: character_scout
kind: character
role: player
description: "Молодой разведчик в коротком зеленом плаще и защитной маске"
view: top_down_three_quarter
canvas_px: [32, 32]
visible_bounds_target_px: [22, 26]
directions: [down, left, right, up]
animations:
  idle: { frames: 4, fps: 6, loop: true }
  run: { frames: 6, fps: 10, loop: true }
  hurt: { frames: 3, fps: 12, loop: false }
  death: { frames: 7, fps: 9, loop: false }
  victory: { frames: 6, fps: 8, loop: false }
pivot_px: [16, 25]
palette: forest_10_colors
background: transparent
export: separate_png_frames
```

`pivot_px` — координата точки опоры внутри логического кадра (для примера — у ног). Если игровой проект задает координаты `0–1`, редактор преобразует их; **в metadata единица должна быть явной**.

### Шаг 2 — создать эталонный спрайт

Сначала генерировать **один** эталонный спрайт `idle/down/frame_000`. Утвердить силуэт, палитру, одежду, пропорции, ракурс и точку опоры.

### Шаг 3 — закрепить identity sheet

Для дальнейших кадров и направлений использовать эталон как визуальный референс, а также явное описание уникальных признаков: положение маски, шов плаща, цвет обуви, форма головы, расположение аксессуаров. Если генератор не поддерживает reference images, потребовать единую pixel spec и использовать ручную коррекцию.

### Шаг 4 — создавать последовательности

Лучше запрашивать **отдельные кадры или небольшой лист со строго известной сеткой**, чем одну огромную генерацию «все анимации сразу»: большой лист чаще дает разные размеры и непредсказуемые позы.

### Шаг 5 — техническая очистка

Прозрачность, canvas, grid alignment, consistency кадров, промежуточные позы, overshoot, palette enforcement, cleanup stray pixels.

### Шаг 6 — импорт и испытание

Загрузить кадры в Animation Studio через drag-and-drop. Настроить FPS, pivot, hitbox, событие урона/выстрела. Посмотреть idle/run/hurt/death/victory на типовом игровом фоне при фактическом масштабе.

### Шаг 7 — сохранить пакет и metadata

Сохранить PNG-файлы и manifest-поля; объект игры ссылается на `spriteId`/`animationId`. Не дублировать последовательность PNG прямо внутри `characters.json`.

## 5. Готовый универсальный промпт для изображения (RU)

> Создай **один игровой пиксельный спрайт** для самостоятельной браузерной 2D top-down roguelike-игры. Сущность: **{ASSET_TYPE}**. Описание: **{DESCRIPTION}**. Размер логического canvas: **{WIDTH}×{HEIGHT} пикселей**. Ракурс: **{VIEW}**, строго согласованный с другими ассетами. Силуэт четкий, читаемый в масштабе 1:1. Ограниченная палитра **{PALETTE}**, чистые квадратные пиксели, целочисленные границы, один условный свет сверху-слева, минимальная пиксельная детализация, аккуратный 1-пиксельный локальный контур. Уникальный оригинальный дизайн, не копировать образы из существующих игр. Для объекта необходим настоящий прозрачный фон (alpha), без тени под объектом, без интерфейса, букв, водяных знаков или сцены вокруг. Центрирование и точка опоры: **{PIVOT}**. Выдать чистый пригодный к импорту PNG, без размытости и псевдопиксельной текстуры. Если система не может соблюсти точную пиксельную сетку или alpha, явно указать, что требуется техническая очистка перед использованием.

**Negative constraints:** no anti-aliasing, no blur, no painterly shading, no soft gradient, no perspective change, no diagonal subpixel lines, no mockup, no environment, no text, no watermark, no checkerboard background, no random props, no inconsistent silhouette.

### Английская версия (для моделей, лучше следующих английским арт-инструкциям)

> Create exactly **one production-ready pixel-art game sprite** for an original 2D top-down roguelike shooter. Asset type: **{ASSET_TYPE}**. Subject: **{DESCRIPTION}**. Logical canvas: **{WIDTH}×{HEIGHT} pixels**. View: **{VIEW}**, consistent with an existing top-down sprite set. Readable silhouette at native size, strict integer pixel grid, crisp edges, limited palette **{PALETTE}**, simple material highlights, subtle top-left lighting and coherent 1-pixel local outline. Truly transparent alpha background (unless asset type is opaque ground tile). No cast shadow outside the sprite, no text, no logos, no UI, no scene, no watermark, no checkerboard backdrop. Character identity, scale, pivot **{PIVOT}** and color placement must match the supplied reference exactly. Do not imitate copyrighted game assets. Output clean PNG intended for nearest-neighbor rendering; if exact pixel grid or alpha cannot be produced, flag manual pixel-cleanup requirement.

## 6. Анимации персонажей — ОБЯЗАТЕЛЬНЫЙ комплект

### 6.1. Состояния

| Animation ID | Обязательна | Поведение | Примерное число кадров |
|---|---|---|---:|
| `idle` | да | Дыхание / покачивание, без движения pivot | 4 |
| `run` | да | Полный цикл шага, разные опоры | 6 |
| `hurt` | да | Читаемый импульс от полученного урона | 3 |
| `death` | да | Падение/исчезновение, сохранять завершающую позу | 7 |
| `victory` | да | Победная поза, ясно читаемая, без оружия в случайной руке | 6 |
| `windup` | опционально для врагов/боссов | Подготовка атаки и телеграф | 4 |
| `attack` | желательно | Исполнение атаки; отдельное событие spawn shot | 4 |
| `reload` | по необходимости | Перезарядка | 5 |

Число кадров и FPS — **стартовые рекомендации**, не фиксированные жесткие лимиты. Все кадры одной анимации одинакового размера canvas; pivot должен оставаться согласованным, иначе спрайт прыгает на месте.

### 6.2. Движение по направлениям

Для top-down игры предпочтительно подготовить `down`, `up`, `left`, `right`. Горизонтальные направления допускают runtime flip **только когда дизайн симметричен** (нет одностороннего знака, щита, асимметричной руки или текста). Прицеливание оружия должно быть отделено от анимаций ног/тела, где это возможно.

### 6.3. Готовый промпт для последовательности кадров

> Создай последовательность **{COUNT} отдельных кадров** анимации **{ANIMATION}** для *того же самого* персонажа, что на предоставленном эталонном спрайте. Каждый кадр ровно **{WIDTH}×{HEIGHT} пикселей**, одна и та же палитра и пиксельная сетка. Направление взгляда **{DIRECTION}**. Фиксированная точка опоры **{PIVOT}**. Меняются только позы, необходимые движению **{ACTION_DESCRIPTION}**. Сохрани форму маски, одежду, цвета, пропорции тела и аксессуары. Не добавляй деталей и новых предметов между кадрами. Настоящая прозрачность фона. Создай кадры в естественном временном порядке, без пропусков фаз движения. Без motion blur, без сглаживания. Экспортируй отдельные PNG `{ASSET_ID}_{DIRECTION}_{ANIMATION}_000.png` ...; если доступен только spritesheet — строго **{COUNT} кадров по горизонтали без полей и смешения анимаций**, сетка **{WIDTH}×{HEIGHT} px**. Отдельно перечисли последовательность и рекомендованные frame durations в мс.

Для `hurt` — 1-й кадр импульс, 2-й пик урона, 3-й восстановление. Для `death` — последовательное падение, на последнем кадре тело/остатки остаются в заданном положении (или отдельно создать death effect). Для `victory` — жест поднятой руки/оружия, не путать с атакой. Для `run` — четкая чередующаяся опора ног. Для `windup` — предварительный визуальный сигнал, без снаряда до момента серверного атакующего события.

### 6.4. Frame/event metadata

Аниматору передать: animation ID, count, FPS/индивидуальную длительность кадров, `loop`, `holdLastFrame`, `pivotPx`, диапазон активных кадров и event hints (`footstep`, `fire`, `hit_flash`, `death_completed`). **Игровой урон не исходит из картинки**; события выполняются игровым движком и синхронизируются с анимацией.

## 7. Оружие, боеприпасы и лучи

### 7.1. Категории

- `melee`: клинок/молот/цепь, отдельный спрайт оружия; хитбокс задается в боевой логике.
- `bullet`: револьвер/автомат, различимый muzzle/barrel direction.
- `shotgun`: широкий ствол, при выстреле можно отдельный sprite muzzle flash.
- `bolt`: арбалет/лук, нужны спрайты стрел/болтов и ориентированная геометрия.
- `laser`: излучатель и текстура/набор сегментов луча, не обычная «пуля».

У каждого оружия сделать `idle` и `fire` при необходимости, origin muzzle point задается в metadata и редакторе, а не определяется цветом пикселя.

### 7.2. Промпт для оружия

> Создай оригинальный пиксельный спрайт оружия **{WEAPON_NAME}**, класс **{WEAPON_CLASS}**; стиль top-down, canvas **{W}×{H}**, направление ствола вправо. Одна отчетливая линия ствола, узнаваемая рукоятка, компактные пиксельные кластеры, палитра **{PALETTE}**, прозрачный фон. Без рук, без владельца, без окружения; спрайт должен поворачиваться вокруг точки `weaponPivot={X,Y}`. Обозначь логическую muzzle-position `{MX,MY}` в отдельном описании. Для laser weapon предоставь отдельные лучевые элементы `beam_start`, `beam_mid`, `beam_end` без перспективного искажения. Для shotgun подготовь один краткий muzzle flash отдельным PNG.

### 7.3. Projectile sprites

Генерировать bullet, pellet, bolt, rocket как отдельные спрайты. `canvas` и `hitbox` различаются, sprite может быть 16×16, collision radius — 2–4 мировые единицы. У projectile обязателен читаемый центр и, если нужен, направление носа (например, вправо). Трейл/взрыв — отдельные particle effects.

## 8. Враги и боссы

### 8.1. Враги

Для каждого типа: уникальная форма тела, размер (например, 32, 48, 64 px), устойчивый силуэт, clear hit flash, idle/run/hurt/death, необязательный `windup` и желательный `attack`. Различать быстрых, дальнобойных, бронированных и поддерживающих врагов по силуэтам/цветовому акценту.

Промпт:

> Создай оригинального врага для top-down pixel roguelike: **{ENEMY_DESCRIPTION}**, роль **{ROLE}**, размер кадра **{SIZE}×{SIZE}**. Он должен читаться как угроза, отличаться от игрока по силуэту, иметь ясную ориентацию и область потенциального урона. Палитра согласованная; пустой прозрачный фон. Отдельно подготовь эталон `idle`, последовательность `run`, `hurt`, `death`, по возможности `windup` (подготовка к атаке) и `attack`. Один и тот же персонаж и pivot на каждом кадре, без изменения костюма. На этапе windup добавь заметный жест подготовки, но не рисуй сам вылет снаряда до fire frame.

### 8.2. Боссы

Босс должен быть большим, но не перегруженным деталями. Промпт должен задавать: `bossId`, игровую роль, число фаз, размеры, silhouette identity, `phase1/phase2` accent colors, `windup`, `attack`, `hurt`, `death`, визуальный телеграф (отдельный effect sprite), phase transition.

Нельзя генерировать полностью разных существ для разных фаз; изменение формы допускается, но должно явно быть частью задания и иметь читаемый переход.

## 9. Уровни, тайлы пола и стен

### 9.1. Обязательные варианты

Для каждого биома генерировать как минимум:

- `floor_base` — повторяемая бесшовная плитка;
- `floor_alt_01..03` — 2–3 вариации для уменьшения тайлинга;
- `floor_decal` — трещины/листья/следы на прозрачном фоне;
- `wall_center`;
- `wall_top`, `wall_bottom`, `wall_left`, `wall_right`;
- четыре внешних и четыре внутренних угла при выбранной autotile-схеме;
- `transition_floor_to_wall` и двери/проемы при необходимости;
- ловушки, опасные тайлы, укрытия, если используются в биоме.

### 9.2. Промпт для бесшовного пола

> Создай **одну бесшовно повторяемую игровую плитку пола** `{BIOME}`: `16×16 px`, строго сверху, оригинальный pixel art, четкие квадратные пиксели, ограниченная палитра, низкий контраст относительно персонажей и снарядов. **Левый край должен бесшовно совпадать с правым, верхний — с нижним**. Изображение заполняет весь canvas, фон НЕ прозрачный. Без крупных объектов, текста, перспективы, градиентов и освещения, которое разрушает повторяемость. Сделай рисунок умеренно случайным, но без заметных повторяющихся символов. Выдай PNG, затем проверь композицию повторением 3×3.

### 9.3. Промпт для стен и autotile

> Создай согласованный набор wall tiles для биома `{BIOME}`: размер каждой плитки `16×16 px`, top-down tilemap. Требуются center, 4 грани, 4 внешних угла, 4 внутренних угла. Все плитки используют общую палитру, толщину контуров, направление освещения и высоту стены. Соседние края должны стыковаться без разрыва геометрии. Не добавляй тени и детали, не совпадающие на границах. Выдай отдельные PNG с однозначными именами; если лист — строгая документированная сетка без дополнительных элементов.

### 9.4. Тесты тайлов

- Тест 3×3 и 8×8 на швы пола.
- Тест всех 4/8 соседей для wall autotile.
- Проверка непрерывности стены и читаемости входов/выходов.
- Тест на типовом масштабе камеры с несколькими врагами и частицами.
- Не допускать слишком ярких деталей пола, визуально похожих на loot.

## 10. Декорации и разрушаемые объекты

Создавать варианты `intact`, `damaged`, `destroyed` — предпочтительно отдельные спрайты/анимации, с единым pivot/размерами. Для пропса задавать графические материалы и механическую роль (к примеру, плотный ящик блокирует пули; травяной куст не блокирует).

Промпт:

> Создай три согласованных состояния оригинального разрушаемого объекта `{PROP_NAME}` в top-down pixel art: `intact`, `damaged`, `destroyed`. Каждый кадр canvas `{W}×{H}`, настоящий alpha, одинаковая основная геометрия и точка привязки. В `damaged` видимые трещины/сколы; в `destroyed` небольшой набор обломков, без изменения ракурса. Отдельно подготовь 2–4 маленьких частицы обломков, которые игра сможет физически разбрасывать. Никаких нарисованных HUD-меток, звуковых обозначений и теней за пределами объекта.

Вероятность появления, прочность и разрушаемость задаются в редакторе игры через JSON, **не зашиваются в графику**.

## 11. Сундуки, pickups и награды

**Сундуки:** closed, opening (3–6 кадров), opened, optionally broken. Отдельные визуальные редкости — common/rare/legendary при необходимости. Читаемая крышка и направление открывания, единый pivot.

**Предметы:** medkit, ammo box, weapon crate, mutation shard, keys. Должны отличаться по контуру, палитре и внутриигровому назначению.

Промпт:

> Сделай пиксельный игровой сундук `{CHEST_ID}` размером `{W}×{H}` для top-down roguelike. Выдай `closed` — закрытую форму; `opening` — 5 последовательных кадров раскрытия крышки; `opened` — окончательное состояние. Одинаковый ракурс, размер, материал, крепления, рисунок древесины/металла, точка опоры на каждом кадре. Никакого лута внутри кадра: отдельные награды и частицы появятся через игровую логику. Истинный прозрачный фон. Простая читаемая форма и чистая пиксельная сетка.

---

## 12. Частицы и эффектные sprites

Графика частиц — это **маленькие текстуры**, а не заранее смоделированная траектория. Скорость, вращение, гравитация, lifetime, alpha fade, spread, drag и collision настраиваются отдельно в `Particle Lab`.

Типовые sprites: spark, smoke, dust, shard, blood fleck (стилизованный, не реалистичный), beam hit, poison bubble, heal cross, explosion fragment.

Промпт:

> Создай небольшой набор независимых оригинальных pixel-art текстур частиц для эффекта `{EFFECT_NAME}`: 6 PNG элементов размера `{4|8|16}×{4|8|16}` каждый, четкий силуэт, строгая пиксельная сетка, единая палитра, прозрачный фон. Никакой заранее нарисованной траектории/дымного облака вокруг сцены: игровой эмиттер будет создавать, вращать, масштабировать и перемещать эти элементы. Экспорт отдельных файлов, без теней и текста.

Для эффекта лазера отдельно предусмотреть `beam_core`/`beam_glow`/`beam_impact` как согласованные тайловые/растягиваемые части; не рисовать готовый луч со сценой и целями.

---

## 13. UI-иконки и портреты

UI должен быть минималистичным: небольшие pixel icons, ясные состояния normal/hover/disabled, никаких надписей внутри текстур. Портреты персонажей могут быть крупнее игровых спрайтов, но должны сохранять лицо/маску/цветовую identity героя.

Интерфейс редактора игры — современный минималистичный UI с обычной гладкой типографикой; **не нужно превращать весь редактор в пиксельный интерфейс**. Пиксельные изображения используются в preview и ассетах игры.

## 14. Совместимость с Editor / JSON / импортом

Для каждого созданного ресурса предоставить `assetId`, `files`, `size`, `pivotPx`, `orientation`, `states`, `licenseNotes`. Пример нейтрального metadata sidecar **для генерации**, который затем преобразуется импортером в `visuals/sprites.json` и `visuals/animations.json`:

```json
{
  "assetId": "character_scout",
  "assetType": "character",
  "logicalFrameSize": { "width": 32, "height": 32 },
  "pivotPx": { "x": 16, "y": 25 },
  "view": "top_down_three_quarter",
  "direction": "down",
  "transparentBackground": true,
  "animations": [
    {
      "id": "idle",
      "fps": 6,
      "loop": true,
      "frameFiles": [
        "character_scout_down_idle_000.png",
        "character_scout_down_idle_001.png",
        "character_scout_down_idle_002.png",
        "character_scout_down_idle_003.png"
      ]
    }
  ]
}
```

Это **не** runtime-формат `characters.json`; это исходные данные Asset Importer. Параметры коллизии, HP, оружия, дропа, анимационных событий, звука и частиц назначаются в соответствующих редакторах.

Структура файлов для одной серии:

```text
assets/
  characters/scout/reference/scout_reference.png
  characters/scout/idle/character_scout_down_idle_000.png
  characters/scout/run/character_scout_down_run_000.png
  characters/scout/hurt/character_scout_down_hurt_000.png
  characters/scout/death/character_scout_down_death_000.png
  characters/scout/victory/character_scout_down_victory_000.png
  enemies/
  bosses/
  weapons/
  projectiles/
  beams/
  environment/forest/floor/
  environment/forest/walls/
  props/
  chests/
  pickups/
  particles/
  ui/
  asset_metadata/
```

## 15. Контрольный список качества (обязателен перед принятием)

**Формат и прозрачность**

- [ ] Четкое целочисленное пиксельное изображение без сглаживания/blur.
- [ ] Верное количество пикселей canvas и известный alpha/opaque режим.
- [ ] Отсутствуют водяные знаки, сетка-превью, подписи и посторонние объекты.
- [ ] Имена файлов/папок и sidecar metadata соответствуют стандарту.

**Визуальная цельность**

- [ ] Персонаж/враг узнается среди других, silhouette читаем в масштабе 1:1.
- [ ] Одинаковая палитра, направление света, масштаб и ракурс.
- [ ] У кадров анимации одинаковые canvas/pivot; нет скачков и потери деталей.
- [ ] Все пять обязательных анимаций игрока: idle, run, hurt, death, victory.
- [ ] Для атакующего врага существует attack, optional windup либо обоснованное отсутствие windup.
- [ ] Босс имеет нужные фазы и согласованные анимации перехода.

**Уровни и эффекты**

- [ ] Пол повторяется 3×3/8×8 без видимых швов.
- [ ] Стены соединяются по углам и сторонам.
- [ ] Враги, pickups и снаряды контрастируют с фоном.
- [ ] Частицы импортируются как независимые маленькие sprites.
- [ ] Сундук и разрушаемый объект имеют согласованные состояния.

**Правовая и техническая проверка**

- [ ] Результат не копирует чужие защищенные ассеты, уникальные персонажи или логотипы.
- [ ] Условия использования генеративной модели допускают предполагаемое коммерческое использование; происхождение ресурсов записано.
- [ ] В импортере проверены размеры, hash, коллизии имен, пути, вирусная/архивная безопасность.
- [ ] Пакет успешно запускается в игровой preview сцене с nearest-neighbor rendering.
